# Module 22 — Notifications & Alerts

## 1. Purpose

A centralized notification **orchestration** system. It notifies farmers,
buyers, transporters, FPO admins, and administrators when something
important happens elsewhere in ANNDATA (a new offer, a payment status
change, a shipment update, a dispute event, a market alert, a security
event, ...). It never duplicates the business logic of the module that
generated the event — it only ever decides WHO should be told, THROUGH
WHICH channel, WITH what message, at what priority, and tracks whether
that delivery actually happened.

## 2. Scope

In scope: a controlled notification-type/event system; a Notification
record (traceable back to its source module/event) fanning out into
per-channel NotificationDelivery rows; a provider abstraction over
in-app/WhatsApp/email/SMS; per-user preferences (including quiet hours and
mandatory security overrides) with sensible lazy defaults; a localized
(en/hi/mr) template system; idempotent creation; retry/failure handling
for transient provider failures via a per-minute cron sweep (this codebase
has no job queue); a paginated in-app inbox API with read/unread/archive
state; ADMIN-authored system announcements fanned out through the same
pipeline.

Out of scope (Section 56): a payment gateway/wallet, fraud detection,
market forecasting, buyer matching, dispute-resolution logic, a second
WhatsApp/email/SMS client, a second audit or queue system, a marketing
automation platform. This module communicates events generated by Modules
6/7/8/13/16/17/18/19/20/21/1 — it is never their source of truth (Section
57): Module 19 remains authoritative for payment status, Module 20 for
financial history, Module 21 for dispute state, Module 6/7/8 for
market/forecast/sell-store data. Module 22 only ever communicates it.

## 3. Architecture

```
ANNDATA BUSINESS MODULES
        |
        v
   DOMAIN EVENTS  (NotificationEventPublisher.notify())
        |
        v
  NOTIFICATION SERVICE  (NotificationService.publish())
        |
   +----+----+
   |         |
RECIPIENT  PREFERENCES
(caller-    (NotificationPreferenceService)
 resolved)
   |         |
   +----+----+
        |
    TEMPLATES  (notification-i18n.ts, en/hi/mr)
        |
     CHANNEL SELECTION
        |
  +-----+-----+-----+
  |     |     |     |
IN-APP WHATSAPP EMAIL SMS  (NotificationProvider implementations)
  |     |     |     |
  +-----+-----+-----+
        |
  DELIVERY STATUS  (NotificationDeliveryService)
        |
  RETRY / FAILURE  (notification-retry.job.ts, per-minute cron)
        |
  AUDIT / HISTORY  (the Notification/NotificationDelivery rows
                     themselves; the audit log for preference/
                     admin-management actions only)
```

Recipient resolution is deliberately NOT re-implemented in this module.
The caller (another module's service, via `NotificationEventPublisher`)
already knows who its own farmer/buyer/FPO admin/transporter user is —
Module 22 only ever receives an already-resolved `recipientUserId`. This
keeps Module 22 from having to understand every other module's ownership
model (FPO-aggregated lots, multi-admin FPOs, etc.).

## 4. Notification types

`NotificationType` (Section 3 of the build spec) covers offers, payments,
shipments, quality/delivery reconciliation, disputes, logistics quotes,
market/forecast alerts, lot changes, account security, and system
announcements — see `prisma/schema.prisma`'s Module 22 section for the
full enum, and `notification.types.ts`'s `NOTIFICATION_TYPE_CATEGORY` map
for which coarse `NotificationCategory` each type is filed under (used for
preference toggles and the `?category=` list filter).

Every type has a localized template (`notification-i18n.ts`) and an
assigned default priority (`notification.types.ts`'s `priorityForType`) —
CRITICAL only for account-security events, HIGH for a small, deliberate
set (payment failure, shipment delay, dispute-response-required, quality
mismatch, logistics-quote-expired), LOW for a small set of routine market/
lot updates, NORMAL otherwise.

## 5. Event integration — wired vs. not yet wired

Every event type above has a real template and a real delivery pipeline
ready for it. Not every source module calls into it yet — the same
"implemented but not every source auto-wired" state Module 20's own
ledger hooks started in:

**Wired today:** Module 21 (`DisputeService`) — `setNotificationHook()`
is called once in `app.ts`, and all five terminal dispute actions
(`create`, `resolve`, `reject`, `reopen`, `close`) call
`notificationHook.notify(...)` right after their own audit record.

**Not yet wired** (Section 22's remaining integration boundaries — each
is the same three-line shape as `DisputeService`'s own
`setNotificationHook` + `notify()` call, added the same way once each
module's own recipient-resolution logic is worked through):
Module 13 (trade offers), Module 16 (logistics quotes), Module 17
(shipments), Module 18 (delivery/quality reconciliation), Module 19
(payments), Module 20 (ledger events), Module 6 (market alerts), Module 7
(forecast alerts), Module 8 (sell/store context changes), Module 4 (lot
changes), Module 1 (login/password-change security events).

`NotificationAnnouncementService` (Section 44 — ADMIN-authored system
announcements) IS fully wired: it fans out through
`NotificationService.publish()` directly, since it does not depend on any
other module's own event stream.

## 6. Notification vs. NotificationDelivery

A `Notification` is one logical "recipient X should know about event Y"
record — the thing a user reads and marks as read/archived. A
`NotificationDelivery` is one channel's attempt to deliver it (one row per
channel actually attempted: IN_APP/WHATSAPP/EMAIL/SMS). One notification
can have several deliveries; reading the notification never touches
delivery state, and a delivery failing never deletes or hides the
notification itself.

## 7. Delivery status semantics

`PENDING -> PROCESSING -> SENT -> DELIVERED`, or `-> FAILED`/`CANCELLED`.
Provider semantics are preserved: an accepted send is only ever `SENT`
(never `DELIVERED`) unless the provider itself confirms delivery — no
channel wired today does, except IN_APP, where "accepted" and "delivered"
are the same event (the row already exists once created).

## 8. Idempotency

`Notification` has a unique constraint on
`(sourceModule, sourceEventId, recipientUserId, type)`. A retried
event (a retried job, a re-delivered webhook, two concurrent workers
racing) resolves to the same single Notification row — enforced at the
database level, not just in application logic (`NotificationRepository
.createIdempotent` catches the resulting `P2002` and looks up the
existing row rather than erroring).

## 9. Retries

Anndata has no job queue (see `whatsapp-recovery.job.ts`'s own comment),
so `notification-retry.job.ts` is a per-minute cron sweep, mirroring that
job's own "recover what a crash left half-done" pattern. It retries:
- deliveries in `FAILED` status that have not exhausted
  `MAX_DELIVERY_ATTEMPTS` (5) — a permanently-failed delivery
  (`retryable: false`, e.g. no linked WhatsApp number, no email on file)
  is never retried in the first place, and
- deliveries stuck in `PENDING`/`PROCESSING` for more than 5 minutes (the
  process crashed mid-send).

The same cron also publishes any ADMIN announcement whose `scheduledFor`
has come due (Section 45).

## 10. Preferences

`NotificationPreference` — one row per user, materialized lazily with
sensible defaults on first read/write (WhatsApp/email on, SMS off, no
quiet hours, no category overrides) rather than a backfill migration.
`NotificationPreferenceService.isChannelEnabled()` is the single gate
`NotificationService` consults per (recipient, category, channel):
IN_APP is always enabled; CRITICAL-priority notifications and the
`ACCOUNT_SECURITY` category always override every other setting
(Section 10/29 — mandatory security notifications can never be silenced).

## 11. Providers

`NotificationProvider` is the shared per-channel contract
(`providers/notification-provider.interface.ts`) — implementations never
throw; a failure resolves to `{ success: false, retryable }` so the
delivery layer can classify it without a try/catch at every call site.

- `InAppNotificationProvider` — trivially always succeeds; the
  Notification row itself is the delivery.
- `WhatsAppNotificationProvider` — reuses the existing Meta WhatsApp
  Business Cloud API integration (`modules/whatsapp`) via the exact same
  `WhatsAppProvider` instance `app.ts` already constructs for the WhatsApp
  Farmer Assistant; resolves the recipient's phone number through the
  existing `WhatsAppLink` table.
- `EmailNotificationProvider` — reuses the existing `EmailService`/
  `EmailProvider` (Module 1's own email infrastructure).
- `UnavailableSmsNotificationProvider` — honest stub. No generic
  transactional-SMS vendor exists in this codebase today (the only SMS
  integration, `TwilioSmsOtpProvider`, is Twilio *Verify*, a one-time-code
  product, not a free-text send API, and reusing it here would misuse a
  verification product as a messaging channel). SMS stays a first-class
  channel in the type system so a real provider can drop in behind this
  same interface later without touching any call site.

## 12. Localization

`notification-i18n.ts` holds one `{en, hi, mr}` template per
`NotificationType` — Anndata's actual account-level language set
(`User.preferredLanguage`), a deliberately separate concern from
WhatsApp's own `{en, hi, hinglish}` conversational language choice in
`whatsapp-i18n.ts`. Placeholders are `{name}`-style and substituted at
render time; a variable the caller didn't supply is left as the literal
placeholder rather than throwing, since a template rendering issue must
never break the business transaction that triggered the notification.

## 13. API

All under `/api`, all requiring authentication, all implicitly scoped to
`req.user` — there is no endpoint that accepts another user's id:

- `GET /api/notifications` — paginated list; `unreadOnly`, `category`,
  `priority`, `from`/`to`, `includeArchived` filters.
- `GET /api/notifications/unread-count`
- `GET /api/notifications/:publicId`
- `POST /api/notifications/:publicId/read`
- `POST /api/notifications/read-all`
- `POST /api/notifications/:publicId/archive`
- `GET /api/notifications/preferences`
- `PATCH /api/notifications/preferences`
- `POST /api/notifications/announcements` (ADMIN only — Section 44)

## 14. Authorization / IDOR

`NotificationAuthorizationService` checks exactly one thing:
`notification.recipientUserId === user.id`. There is no admin override —
Section 31: "Admins should not automatically see everyone's private
notifications unless the existing admin architecture explicitly requires
it," and it does not, for this module.

## 15. Data privacy

`Notification.metadata` is free-form JSON but is expected to hold only
non-sensitive template context — never OTPs, tokens, credentials, or raw
provider payloads (Section 42). `NotificationDelivery.failureReason` is
always a sanitized string, never a raw provider error body.

## 16. Frontend

Not implemented in this pass — this module ships the backend API only.
The existing design system's notification-bell/unread-badge/inbox
components (if any) should consume the endpoints in Section 13 directly;
`GET /api/notifications/unread-count` is intended for a polling or
Socket.IO-driven badge (no Socket.IO/real-time layer exists in this
codebase today, so polling is the interim answer).

## 17. Known limitations / follow-ups

- Most business-module event sources are not yet auto-wired (Section 5)
  — the pipeline, templates, and API are complete and tested at the unit
  level the codebase's own conventions expect, but firing them from
  Module 13/16/17/18/19/20/6/7/8/4/1 is future work, each a small,
  well-scoped addition following `DisputeService`'s own pattern.
- No SMS vendor is wired (Section 11) — by design, since none exists in
  this codebase; the channel is ready for one.
- No automated test suite was added in this pass (see the module's own
  final report for why).
- `npx prisma format/validate/generate` could not be run in the sandbox
  this module was built in — network egress is restricted to an allowlist
  that excludes `binaries.prisma.sh`. The migration was hand-authored
  instead (following the exact precedent already set by this repo's own
  Module 16–21 migrations) and should be applied, then followed by
  `npx prisma generate`, in an environment with normal network access.
